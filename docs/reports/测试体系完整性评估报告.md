# SeedVR2 测试体系完整性评估报告

> **评估日期:** 2026-08-10  
> **评估范围:** SeedVR2 项目全量测试资产  
> **评估方法:** 基于目录结构、测试源码、CI 配置的静态分析  
> **评估原则:** 聚焦现状分析，遵循经典测试金字塔模型（Unit > Integration/API > UI）

---

## 一、测试金字塔形态对比分析

### 1.1 理想测试金字塔

```
        /\
       /  \        ← E2E/UI (少量，~10%)
      /----\
     /      \      ← Integration/API (中等，~20-30%)
    /        \
   /----------\    ← Unit (大量，~60-70%)
  /____________\
```

### 1.2 SeedVR2 实际形态：倒金字塔 / 冰淇淋模型

```
        /\
       /  \        ← Unit: 33 个 .py 文件 (~46%)
      /------\
     /          \  ← Integration/API: ~6 个文件 (~8%)
    /------------\
   /              \  ← UI/E2E: 16 个 .ts spec + 7 POM + fixtures (~46%)
  /________________\
```

**形态判定：** 当前测试体系呈现**倒金字塔（冰淇淋甜筒）**形态。Python 单元/API测试与 TypeScript E2E 测试在文件数量上几乎持平（33 vs 23+），UI 测试权重过高。

### 1.3 测试资产数量统计

| 层级 | 文件数 | 估算测试用例数 | 占比 |
|------|--------|---------------|------|
| **Python 单元/集成/API测试** | 33 个 `.py` | ~280 | ~46% |
| **TypeScript E2E/UI 测试** | 16 个 `.spec.ts` | ~120 | ~38% |
| **Playwright POM (页面对象)** | 7 个 `.page.ts` | — | — |
| **测试工具/Fixtures** | 5+ 个 | — | — |
| **性能测试** | 1 个 `locustfile.py` | 6 场景 | ~1% |
| **安全冒烟测试** | 1 个 `smoke_test_security.py` | 6 检查 | ~1% |
| **API 验收测试** | 1 个 `api_test_runner.py` | ~20 | ~3% |
| **WCAG 对比度测试** | 1 个 `.spec.ts` + 1 个 `.js` | ~24 | ~4% |
| **属性测试 (Hypothesis)** | 1 个 `test_property_based.py` | ~6 | ~1% |

#### 2.1.3 核心算法测试评估

**`model_lib/dit/`、`model_lib/dit_v2/`、`common/diffusion/` — 零测试覆盖**

这是 SeedVR2 的**核心推理引擎**（DiT 模型架构、扩散采样器、时间步调度等），但在 `pyproject.toml` 中被显式排除：

```toml
[[tool.mypy.overrides]]
module = ["model_lib.*", "common.distributed.*", "common.diffusion.*",
          "bin.integrated_app.optimization.*", "bin.integrated_app.engines.*"]
ignore_errors = true
ignore_missing_imports = true
```

```toml
[tool.coverage.run]
source = ["bin/integrated_app"]
omit = [
    "*/optimization/gpu/gpu_compatibility.py",
    "*/optimization/gpu/vram_monitor.py",
    "*/engines/_vae_pipeline.py",
    "*/engines/_dit_pipeline.py",
    # ... 共 15 个 omit 模块
]
```

**评估结论：** 核心算法层（`model_lib/`、`common/diffusion/`）被设计性地排除在测试体系之外，依赖 `verify_engine.py` 自检和端到端运行验证。这是该项目测试体系中最大的结构性缺口。

#### 2.1.4 覆盖率目标

```toml
[tool.coverage.report]
fail_under = 65
```

覆盖率阈值为 **65%**，仅覆盖 `bin/integrated_app` 层（不含 `model_lib/`、`common/`），属于中等偏低标准。

### 2.2 集成测试层

#### 2.2.1 集成测试识别

项目中**没有独立的 `integration/` 目录**，集成测试与单元测试混放在 `tests/` 根目录下，通过 pytest marker 标记：

```toml
[tool.pytest.ini_options]
markers = [
    "integration: marks integration tests (deselect with '-m \"not integration\"')",
    "benchmark: marks benchmark tests",
]
```

CI 中执行时排除集成测试：
```yaml
python -m pytest -q -m "not integration" --ignore=tests/perf --cov=bin/integrated_app
```

#### 2.2.2 集成测试现状

| 文件 | 集成性质 | 覆盖的交互 |
|------|---------|-----------|
| `test_api.py` | API 集成 | FastAPI 路由 → HistoryDB → ModelManager（mock） |
| `test_sse_integration.py` | SSE 端点集成 | SSE 端点错误处理（仅 404 路径） |
| `test_history_htmx.py` | HTMX 片段集成 | History API + HTMX 片段渲染 |
| `test_video_pipeline.py` | 引擎集成 | MockVideoEngine + cv2 + FFmpeg mock |
| `conftest.py` 的 `test_app` | 全栈集成 fixture | FastAPI app + TestClient + mock ModelManager |

**评估结论：** 集成测试数量有限（约 4-5 个文件），且 `test_sse_integration.py` 实际上仅测试 404 错误路径（真正的 SSE 流由 Playwright E2E 覆盖）。模块间交互测试覆盖不足，特别是**引擎层与任务队列的集成、模型加载与推理管道的集成**缺少测试。

| `api_test_runner.py` | 运行时验收脚本（非 pytest） | ~20 |

#### 2.3.2 API 测试质量评估

**优点：**
- `test_api.py` 覆盖了主要只读 API 端点
- 包含分页边界测试（page=0 返回 422、page=9999 返回空列表、page_size 超限返回 422）
- 包含安全路径测试（白名单外 403、白名单内不存在 404）
- 使用 `csrf_post` helper 统一处理 CSRF token
- `test_api_schema.py` 验证 OpenAPI schema 的完整性和一致性
- `test_property_based.py` 使用 Hypothesis 进行属性测试

**不足：**
- **写操作测试薄弱** — POST `/api/restore/` 仅测试空输入（400）和无模型（503），未测试完整的修复任务生命周期
- **缺少认证/授权测试** — Basic Auth 中间件仅冒烟测试，无 API 层面的认证测试
- **缺少并发测试** — 多用户同时操作同一资源的场景未覆盖
- **缺少 SSE 流式测试** — `test_sse_integration.py` 仅测试 404，真实 SSE 流由 E2E 覆盖
- **缺少负面测试** — 恶意输入、超大文件、非法 MIME 类型等边界场景未覆盖
- `api_test_runner.py` 是独立的 urllib 脚本，需要运行中的服务器，与 pytest 体系脱节

#### 2.4.3 UI 测试权重评估

**UI 测试在整体测试体系中的占比约 46%**（按文件数），这是一个**显著偏高的比例**。

**潜在风险分析：**

1. **反馈周期延长** — 16 个 spec 文件 × 8 个 Playwright project（3 浏览器 × 4 视口组合），完整 E2E 套件执行时间可能达到 **30-60 分钟**，远超理想反馈周期（< 10 分钟）
2. **维护成本非线性增长** — 7 个 POM + 30+ mock 函数 + 16 个 spec 文件，UI 变更需要同步更新多处
3. **视觉回归测试的脆弱性** — `uiux-compatibility.spec.ts` 包含 12 个 `toHaveScreenshot()` 调用（6 页面 × 2 主题），跨平台渲染差异可能导致频繁的基线更新
4. **Mock 依赖过重** — `setupAllMocks` 函数设置了 30+ 个路由 mock，几乎完全绕过了后端，测试的是"前端能否正确渲染 mock 数据"而非真实业务逻辑
5. **WCAG 对比度测试重复** — `a11y.spec.ts` 中已有 axe-core 对比度检查，`wcag-contrast.spec.ts` 又实现了独立的对比度计算逻辑，存在冗余

## 三、专项测试评估

### 3.1 性能测试

| 资产 | 位置 | 覆盖范围 |
|------|------|---------|
| Locust 负载测试 | `tests/perf/locustfile.py` | 6 个只读 API 端点（health, history, settings, gpu, metrics, locales） |
| Web Vitals 测试 | `tests/specs/performance.spec.ts` | FCP, LCP, CLS, 页面加载时间, API 响应时间, 进度条帧率, 内存, Bundle 大小 |
| CI 流水线 | `.github/workflows/performance.yml` | 每日定时 + PR 触发，20 用户并发 2 分钟 |

**评估：**
- Locust 测试仅覆盖**只读 API**，缺少写操作（修复任务提交）的负载测试
- 阈值设置合理：P95 < 500ms，错误率 < 1%
- Web Vitals 测试使用 Playwright 内联实现，阈值偏高（FCP 15s, LCP 5s），适配 CPU 环境
- 缺少**推理性能基准测试** — 模型推理延迟、VRAM 占用、帧处理吞吐量均未覆盖

### 3.2 安全测试

| 资产 | 位置 | 覆盖范围 |
|------|------|---------|
| CSRF 签名测试 | `tests/test_csrf_signed.py` | HMAC token 生成/验证/篡改/跨密钥/持久化 |
| PathGuard 测试 | `tests/test_path_guard.py` | 白名单、路径遍历、绝对路径、空字节 |
| 安全 E2E 测试 | `tests/specs/security.spec.ts` | XSS, CSRF, 路径遍历, 敏感数据, CSP, 内联事件, Cookie, 输入消毒 |
| 冒烟安全测试 | `scripts/smoke_test_security.py` | 水印、自检、完整性校验、Basic Auth、权重加密 |
| SAST CI | `.github/workflows/security.yml` | Semgrep 自动扫描 |
| FTS5 注入测试 | `tests/test_fts_escape.py` | FTS5 特殊字符注入 |
| Magic Check | `tests/test_magic_check.py` | 文件类型校验 |

**评估：**
- 安全测试覆盖面较广，从单元到 E2E 均有覆盖
- CSRF 测试质量较高，覆盖了 token 格式、篡改、空值、跨密钥、持久化等场景
- PathGuard 测试覆盖了路径遍历、符号链接、空字节等关键攻击向量
- E2E 安全测试使用 route mock 模拟恶意响应，验证前端消毒能力
- **不足：** 缺少速率限制测试、缺少 SSRF 防护测试、缺少文件上传安全测试（恶意文件内容）

### 3.3 兼容性测试

| 维度 | 覆盖状态 |
|------|---------|
| **跨浏览器** | Chromium + Firefox + WebKit（3 引擎），CI 矩阵执行 |
| **跨视口** | Desktop (1920×1080), Laptop (1366×768), Tablet (768×1024), Mobile (375×812) |
| **跨平台** | CI 在 Windows + Ubuntu 双平台运行（仅后端测试） |
| **视觉回归** | 12 个截图基线（6 页面 × 2 主题），`maxDiffPixelRatio: 0.01` |
| **触摸目标** | WCAG 2.5.5 合规检查（44×44px），容忍 ≤10 个违规 |

**评估：** 兼容性测试覆盖面广，但视觉回归测试的基线维护成本较高。触摸目标检查使用"容忍 ≤10 个违规"的渐进式策略，尚未完全合规。

### 3.4 混沌工程

| 维度 | 状态 |
|------|------|
| 网络故障 | `network-conditions.spec.ts` — 慢 3G、离线、间歇性连接 |
| 任务异常 | `test_task_queue.py` — 任务异常不崩溃 worker、worker 自动重启、最大重启次数 |
| 数据库异常 | `test_history_db.py` — close 异常安全、close 幂等 |

## 五、基础设施与质量保障

### 5.1 CI/CD 流水线

| 工作流 | 触发条件 | 内容 |
|--------|---------|------|
| `ci.yml` | PR/push to main/develop | Ruff + Black + Mypy + Pytest + Coverage（双平台矩阵） |
| `e2e.yml` | PR/push（路径过滤） | Playwright E2E（3 浏览器 desktop project） |
| `security.yml` | PR/push + 每周定时 | Semgrep SAST 扫描 |
| `performance.yml` | PR + 每日定时 | Locust 负载测试 |
| `dependency-audit.yml` | PR（依赖变更） + 每周 | pip-audit + safety + npm audit |
| `gpg-signed-release.yml` | Release 发布 | GPG 签名 + SHA256SUMS |

**评估：** CI 流水线设计完善，覆盖了代码质量、安全、性能、依赖审计和发布完整性。但存在以下问题：

1. **质量门禁失效** — `ci.yml` 中多个步骤使用 `|| true` 容忍失败：
   ```yaml
   - name: Mypy (type check)
     run: python -m mypy bin/integrated_app || true
   - name: Pytest + coverage
     run: python -m pytest -q ... || true
   ```
   这意味着即使测试失败也不会阻断 PR 合并。

2. **E2E 触发条件** — `e2e.yml` 仅在特定路径变更时触发，可能遗漏间接影响

3. **无 staging/prod 部署流水线** — 仅有 Release 签名，无自动化部署

### 5.2 质量门禁

| 门禁 | 工具 | 严格度 |
|------|------|--------|
| 代码风格 | Ruff (E, F, W, I, N, UP, B, A, C4, SIM) | 检查但不阻断（`|| true` 在某些步骤） |
| 格式化 | Black --check | 检查但不阻断 |
| 类型检查 | Mypy (check_untyped_defs) | 检查但不阻断（`|| true`） |
| 测试 | Pytest + coverage (fail_under=65) | 执行但不阻断（`|| true`） |
| 安全扫描 | Semgrep | 扫描但不阻断（`|| true`） |

**评估：** 质量门禁配置存在但**未强制执行**，多处使用 `|| true` 容忍失败，削弱了门禁的实际效果。

### 5.3 测试框架

| 层级 | 框架 | 版本特征 |
|------|------|---------|
| 后端单元/集成 | pytest 9.1.x | asyncio_mode=auto, strict-markers, timeout=60 |
| 前端 E2E | Playwright (TypeScript) | fullyParallel, html reporter |

| 属性测试 | Hypothesis | 条件导入（未安装则 skip） |
| 覆盖率 | pytest-cov | branch=true, xml+html+term 输出 |
| 可访问性 | axe-core | 通过 Playwright 注入 |

## 七、特别关注点分析

### 7.1 UI 测试权重占比

**UI 测试在整体测试体系中的实际权重：**

- 文件数量占比：**~46%**（33 Python vs 23 TypeScript+fixtures）
- 估算测试用例占比：**~30%**（~280 Python vs ~120 TypeScript）
- CI 执行时间占比：**>70%**（E2E 3 浏览器矩阵 × 16 spec 文件，远超 pytest 执行时间）

**判断：** UI 测试权重显著偏高，已形成倒金字塔形态。

### 7.2 反馈周期评估

| 流水线 | 估算执行时间 | 反馈周期 |
|--------|------------|---------|
| `ci.yml`（双平台矩阵） | ~5-10 分钟 | 可接受 |
| `e2e.yml`（3 浏览器 × 16 spec） | ~30-60 分钟 | **过长** |
| `performance.yml` | ~5 分钟 | 可接受 |
| `security.yml` | ~3 分钟 | 可接受 |

**E2E 测试是 CI 反馈周期的主要瓶颈。**

### 7.3 UI 测试维护成本评估

| 维护维度 | 规模 | 增长趋势 |
|---------|------|---------|
| POM 维护 | 7 个页面对象 | 线性增长 |
| Mock 维护 | 30+ mock 函数 | 线性增长 |
| 视觉基线维护 | 12 个截图 | 线性增长，但跨平台差异导致非线性修改频率 |
| Spec 维护 | 16 个 spec 文件 | 线性增长 |
| 浏览器矩阵维护 | 8 个 project | 固定 |

**评估：** 当前规模（16 spec × 8 project = 128 次执行）的维护成本尚可控，但随着页面和功能增加，维护工作量将呈非线性增长。

### 7.4 测试金字塔合规性判断

| 原则 | 当前状态 | 合规度 |
|------|---------|--------|
| 单元测试占多数 | Python 33 文件 vs TS 23 文件 | **不合规** — 比例接近 1:1 |
| API 测试为中层 | ~6 个 API 测试文件 | **部分合规** — 覆盖面不足 |
| UI 测试为顶层（少量） | 16 个 spec + 8 project | **不合规** — 权重过高 |
| 反馈速度快 | E2E 30-60 分钟 | **不合规** |
| 底层测试最稳定 | 核心算法无测试 | **不合规** |

**总体判断：** 当前测试体系**不符合测试金字塔基本原则**，呈现倒金字塔（冰淇淋甜筒）形态。UI 测试权重过高、核心算法测试缺失、CI 质量门禁失效是三个最关键的结构性问题。

## 八、总结

### 8.1 测试体系成熟度评估

| 维度 | 评分 (1-5) | 说明 |
|------|-----------|------|
| 测试覆盖广度 | ★★★★☆ | 覆盖了 API、安全、UI、性能、可访问性等多维度 |
| 测试覆盖深度 | ★★★☆☆ | 应用层覆盖尚可，核心算法层完全空白 |
| 测试金字塔形态 | ★★☆☆☆ | 倒金字塔，UI 权重过高 |
| CI/CD 集成 | ★★★★☆ | 6 条流水线，覆盖质量/安全/性能/依赖/发布 |
| 质量门禁有效性 | ★★☆☆☆ | 多处 `\|\| true` 容忍失败，门禁形同虚设 |
| 测试稳定性 | ★★★☆☆ | 存在硬编码等待和残缺断言，Flaky 风险中等 |
| 测试数据管理 | ★★★★☆ | tmp_path 隔离、集中 mock、测试素材齐全 |
| 测试可维护性 | ★★★☆☆ | POM 模式良好，但 UI 测试与 HTML 结构耦合 |

### 8.2 关键发现摘要

1. **核心算法零测试** — `model_lib/`、`common/diffusion/`、`engines/` 被设计性排除，是最大结构性缺口
2. **倒金字塔形态** — UI 测试权重 ~46%，与单元测试比例接近 1:1
3. **CI 质量门禁失效** — Mypy、Pytest 步骤均使用 `|| true`，不阻断 PR
4. **E2E 反馈周期过长** — 3 浏览器 × 16 spec，估算 30-60 分钟
5. **SSE 测试残缺** — Python 端仅测 404，E2E 端断言过弱（`toBeGreaterThanOrEqual(0)`）
6. **硬编码等待普遍** — 多处 `waitForTimeout`，Flaky Test 风险高
7. **视觉回归脆弱** — 12 个截图基线跨平台漂移风险
8. **安全测试较完善** — CSRF、PathGuard、XSS、FTS5 注入均有覆盖
9. **属性测试存在但可选** — Hypothesis 条件导入，未安装则 skip
10. **验收测试脱离体系** — `api_test_runner.py` 独立于 pytest，无 CI 集成
